# Rails on Wodby

What this service adds to the Ruby service it is based on. Check it before adding database, secret key, host or job queue settings to the application.

## Variables the service sets

| Variable | Meaning |
| --- | --- |
| `RAILS_ENV` | `development` in environments of type `dev`, `production` in every other type (`prod`, `staging`, `test`, `feature`). An environment of type `test` is a deployed application, not Rails' test environment. |
| `SECRET_KEY_BASE` | A secret generated by Wodby for the service. Rails reads it by itself. Do not generate or commit another one. |
| `WORKSPACE_RUBY_COMMAND` | The start command of a development workspace, see below. |

`RAILS_MASTER_KEY` is not set. An application with encrypted credentials provides its own key as a secret variable on the service.

## Linked services

In addition to the variables of the Ruby service:

| Link | Variable |
| --- | --- |
| Database | `DATABASE_URL`, the whole connection as one URL, with credentials |
| Redis or Valkey | `REDIS_URL`, a `redis://` URL with the password, database `0` |

Rails reads `DATABASE_URL` by itself, and its values take precedence over the same keys in `config/database.yml`. Do not put a host, user or password in `database.yml`. Nothing configures a job queue, cache or mailer for the application: it decides what to do with `REDIS_URL`, `SMTP_HOST` and `SMTP_PORT`, and must start without them when the link is absent. Both URL variables hold a password: never print or commit their values.

## Host authorization

The service mounts a config file, named Host authorization, into the container at `/usr/src/app/config/initializers/wodby_host_authorization.rb`. It is not part of the repository, and it is changed as a config of the service on Wodby, not in the code. When `WODBY_HOSTS` or `WODBY_APP_SERVICE_NAME` is present it:

- adds every host of the environment and the service's internal host name to `config.hosts`;
- sets `config.host_authorization` to exclude requests whose path is `/healthz`.

Do not add the environment's hosts to `config.hosts` in the code. Serve the health endpoint at `/healthz` so that it works without a known host header.

## Build

The service's Dockerfile installs `vips`, runs `bundle install`, and runs `rails assets:precompile` with `RAILS_ENV=production` and a dummy secret key when the application has that task. The runtime variables and the database are not available during the build.

## After a deployment

1. `bundle exec rails db:prepare` runs after every deployment of the service. It prepares the linked database: schema and pending migrations.
2. `bundle exec rails db:seed` runs after it, during the first deployment only.

The start command and the pipeline do not have to run migrations.

## Server

The container starts Puma as described for the Ruby service: port 8080, the image's generated configuration, not the application's `config/puma.rb`. Rails takes its environment from `RAILS_ENV`.

## Sidekiq worker

The optional `rails-sidekiq` service runs `bundle exec sidekiq` instead of Puma. It needs `sidekiq` in the `Gemfile`. Sidekiq reads `REDIS_URL` by itself.

## In a development workspace

- The application is started with `bundle exec rails server --binding "$HOST" --port "$PORT"`, on port 8080, with `RAILS_ENV=development` whatever the environment type.
- Migrations and seeds are not run by starting the server.
- Rails reloads application code between requests in development. The checkout is on network storage, where an evented file watcher is not reliable: `config.file_watcher` must be `ActiveSupport::FileUpdateChecker`, which is Rails' default.

## Check the result

- `bundle exec rails runner 'puts ActiveRecord::Base.connection.adapter_name'` shows whether the database link works.
- `bundle exec rails runner 'puts Rails.application.config.hosts.inspect'` shows the allowed hosts.
- `bundle exec rails db:migrate:status` shows the applied migrations.
